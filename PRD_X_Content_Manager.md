# PRD — X Content Manager

Версия: 0.1 · 28 сентября 2026 · Статус: проектное задание для проверки и реализации

## 1. Идея и цель

Веб-приложение для автора X: планировать собственные публикации с медиа, управлять повторным продвижением своих постов через Repost, находить подходящие чужие посты для осмысленного ответа, сохранять историю действий и понимать стоимость и результат. Сначала один пользователь, затем отдельный аккаунт для друга; платная подписка возможна позже.

Продукт **не обещает подписчиков**. Главная проверяемая гипотеза: удобное планирование публикаций и ручной отбор ответов позволяют вести аккаунт последовательнее, а измерения помогают понять, какие действия совпадают с ростом охвата и аудитории. Корреляцию нельзя выдавать за доказанное влияние конкретного действия.

## 2. Пользователи и границы

- Автор: подключает свой X-аккаунт через OAuth, загружает только контент, на который имеет права, планирует публикации, утверждает ответы, видит результаты.
- Друг автора: отдельная учётная запись, собственный workspace и X-аккаунт, без доступа к данным автора.
- В первой реализации один workspace на пользователя и один X-аккаунт на workspace. Схема допускает дополнительные аккаунты и участников позже, но UI команд, роли и биллинг не нужны.
- Целевая аудитория будущей версии: авторы контента, которым нужен редакционный процесс и контроль расходов. Перед продажей проверить условия X API, использования данных и выбранного хостинга.

## 3. Обязательная проверка до основной разработки (Gate 0)

В Developer Console X проверить реальную доступность, OAuth scopes, стоимость и лимиты для: публикации поста, загрузки изображения и видео, Repost, чтения постов указанных пользователей, чтения собственных метрик и счётчика подписчиков. Сделать минимальные разрешённые тестовые запросы и документировать endpoint, scope, цену, единицу тарификации, лимит, ошибки и итог за один сценарий. Отдельно проверить допустимость сценария приложения для нескольких независимых пользователей и будущей коммерческой версии.

Публичная документация X на дату PRD описывает оплату по использованию: чтение Posts — $0.005 за возвращённый ресурс, User — $0.010 за ресурс, создание Post — от $0.015 за запрос; для создания с URL указан иной тариф. Цены меняются, поэтому Console является источником окончательной сметы. Например 10 аккаунтов × 3 возвращённых поста × 2 проверки в день × 30 дней = 1800 прочитанных постов, или приблизительно $9 **только за эти reads** по приведённой ставке; это не цена всего приложения. Кэширование и повторные чтения проверить на фактическом биллинге. [X pricing](https://docs.x.com/x-api/getting-started/pricing).

**Gate 0 проходит**, если базовые write/read сценарии доступны, стоимость прогнозируема в заданном месячном бюджете, а расписание может исполняться с выбранной точностью. Если чтение чужих постов слишком дорого, оставить ручное добавление URL и запуск анализа по требованию. Если публикация недоступна, остановить автоматизацию и пересмотреть MVP.

## 4. Правила поведения продукта

- Для действий в X использовать только официальный API. Не автоматизировать сайт X через браузер, DOM или скрипты.
- Не делать автоматические лайки, массовые подписки, автоответы незнакомым аккаунтам, похожие массовые публикации и агрессивные циклы Repost.
- AI лишь предлагает текст и медиа. Ответ на чужой пост отправляется **только после явного нажатия пользователем Publish**, с возможностью отредактировать и отменить. Одно нажатие утверждает один конкретный ответ на один пост. Не делать пакетное подтверждение и автоотправку.
- Подготовленный self-reply тоже требует ручного подтверждения на старте. Проверить актуальные правила перед изменением поведения.
- Автоматический Repost своего поста разрешать только для заранее заданного пользователем действия, с предупреждением и редкими интервалами; никаких бесконечных циклов или автоматического Repost из сигналов вовлечённости.
- Поддержать маркировку sensitive media и настройки аккаунта, если они применимы. Отдельно оценить политики медиа до публикации соответствующего контента.
- Не использовать в интерфейсе или продвижении обещания вроде «получи больше подписчиков»: правила X отдельно ограничивают приложения, заявляющие такую цель. [X automation rules](https://help.x.com/en/rules-and-policies/x-automation).

## 5. MVP: функциональные требования

### 5.1 Доступ и изоляция

Регистрация/вход пользователя; создание workspace; подключение собственного X-аккаунта через OAuth; просмотр статуса подключения, обновление и отзыв доступа. Каждый запрос авторизует пользователя и workspace. Секреты и токены доступны только серверу, шифруются при хранении. При отсоединении аккаунта запланированные задания останавливаются.

### 5.2 Библиотека медиа

Загрузка изображения/видео в приватное хранилище, превью, описание, теги, тип, размер, дата, история использования. Проверка типа/размера и ограничений X до постановки в очередь. Метаданные AI по желанию создаются один раз при загрузке; автор может их исправить. Видео может требовать отдельного workflow загрузки и обработки X; после Gate 0 допустимо начать с изображений, но видео остаётся запланированным требованием.

### 5.3 Публикация и расписание

Создать черновик с текстом и медиа; предварительный просмотр; выбрать дату и время в часовом поясе пользователя, хранить UTC и исходный timezone; редактировать/отменять до начала исполнения. Состояния: DRAFT → SCHEDULED → PROCESSING → PUBLISHED / FAILED / UNKNOWN. Сохранять X post ID и время отправки.

Планировать однократный Repost собственного опубликованного поста на выбранное время. По умолчанию отключён. Показать близкие уже запланированные действия и ограничить повторное выполнение. Подготовка self-reply с текстом и дополнительным медиа: напоминание/карточка для ручного Publish.

После таймаута при записи в X результат может быть неизвестен: **не повторять слепо**. Сначала сверять результат доступным способом; если надёжно установить факт публикации нельзя, перевести в UNKNOWN и потребовать ручную проверку. Локальная блокировка/уникальный ключ защищает от параллельных воркеров, но не обеспечивает сквозную идемпотентность X API.

Точность расписания задаётся после выбора исполнителя. Vercel Hobby Cron сейчас запускается не чаще раза в сутки и может сдвигаться почти на час: для времени публикации с точностью порядка минуты нужен иной план или scheduler. Интерфейс должен честно показывать гарантируемую точность. [Vercel Cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing).

### 5.4 Engagement Inbox

Ручной список target accounts. Начать с небольшого числа и чтения по запросу; фоновое чтение включать только при подтверждённой экономике X API. Для каждого нового post ID: сохранить краткие данные и время; применить локальные фильтры (возраст, приоритет, повторы, cooldown, темы); предложить релевантность и черновик ответа через AI для малого набора кандидатов. Показать исходный пост, автора, дату, доступные метрики, источник, предложение AI и медиа. Действия: Edit, Change media, Publish, Skip. Перед отправкой проверить, что пост доступен, пользователь уполномочен и ответ ещё не отправлен этим аккаунтом через приложение.

Если API чтения недоступен или дорог: пользователь вставляет URL поста; если получение данных через разрешённый API недоступно, разрешить ручной ввод контекста и открытие X для ручного действия. Не подменять API скрейпингом.

### 5.5 История, измерения и расходы

История попыток и результатов с отдельными событиями post/repost/self-reply/ответа. Снимки доступных метрик собственного поста и общего числа подписчиков с отметкой времени. Не показывать «сколько подписчиков принёс конкретный комментарий», если такой метрики нет. Сравнение типов действий и интервалов — описательная аналитика с числом наблюдений, без заявлений о причинности. Доступность private/organic metrics и 30-дневное окно проверить по OAuth и endpoint. [X metrics](https://docs.x.com/x-api/fundamentals/metrics).

Показывать расходы X и AI по workspace, по месяцу и по операции. Бюджетный предел приложения останавливает *новые фоновые чтения/AI вызовы* до увеличения лимита; запланированные записи не должны тихо исчезать — уведомлять о невозможности исполнения. Реальная сумма X сверяется с Console; локальный расчёт приблизителен.

## 6. Нефункциональные требования

- Данные каждого workspace изолированы на уровне запросов и service/repository API; запрещены неограниченные выборки пользовательских данных. Проверить cross-workspace IDOR тестами.
- У cron endpoint отдельная серверная авторизация; подбор due jobs выполняется на сервере, с атомарным claim и lease; статусы и audit log доступны владельцу.
- OAuth state + PKCE, минимальные scopes, безопасная сессия, шифрование токенов с ротацией ключей, отсутствие ключей в клиентском bundle и логах.
- Входящие AI-поля и внешние ответы валидируются через Zod. Текст X-поста считается недоверенными данными, не может диктовать инструменты AI или публикацию.
- Лимиты бюджета, backoff на 429, обработка истёкших токенов и явная ошибка пользователю; не обходить rate limits.
- Приватные медиа по умолчанию; ограниченный доступ, удаление файлов и пользовательских данных; политика хранения данных X перед beta.
- Времена сохранять в UTC; отображать в зоне пользователя. Наблюдаемость: структурированные ошибки с action ID без токенов, метрики удачных/неудачных задач.

## 7. Предлагаемый стек и схема

- Next.js App Router, React, TypeScript strict, Tailwind; TanStack Query только где полезны клиентские обновления.
- Next.js Route Handlers + небольшие server services; PostgreSQL + Prisma; Supabase Postgres/Storage как вариант. Проверить соединения Prisma и лимиты выбранного тарифа.
- Auth: выбрать конкретный провайдер после spike, не смешивать app login с OAuth X.
- AI: тонкий интерфейс провайдера, один недорогой модельный путь для коротких ответов и опциональный vision при загрузке. Вызовы и цены учитывать на сервере.
- Jobs: интерфейс `processDueActions(now, batchSize)` отделён от триггера. Vercel Cron только при подходящем тарифе и точности; альтернативный scheduler выбирается по фактической стоимости и SLA. Redis/BullMQ не нужен заранее.

Минимальные таблицы: `User`, `Workspace`, `WorkspaceMember` (если auth-модель требует; иначе `ownerId` достаточно до приглашений), `XAccount`, `Media`, `Post`, `ScheduledAction`, `TargetAccount`, `CandidatePost`, `ReplySuggestion`, `ActionAttempt`, `MetricSnapshot`, `FollowerSnapshot`, `ExternalUsage`. У каждой пользовательской сущности явная связь с workspace/аккаунтом и соответствующие индексы/уникальности. Не хранить дублирующие идентификаторы без необходимости; схему утвердить после Gate 0.

## 8. Последовательность реализации и критерии готовности

| Этап | Результат | Условие завершения |
|---|---|---|
| 0. Feasibility | Матрица API/scopes/cost + выбор scheduler и бюджет | Подтверждён доступ к нужным базовым операциям, понятна точность и месячный прогноз |
| 1. Foundation | App auth, workspace, DB, X OAuth | Два тестовых пользователя не видят ресурсы друг друга; токены хранятся серверно |
| 2. Publish spike | Текстовый тестовый пост через API | ID сохранён; ошибки и неизвестный исход обработаны; запись только после явного разрешения автора |
| 3. Media + scheduling | Медиа, черновики, время, job processor | Пост публикуется один раз; редактирование/отмена и timezone работают |
| 4. Repost + self-reply | Однократный Repost, подготовка ручного follow-up | Никаких повторов при параллельном/повторном вызове; self-reply требует клика |
| 5. Engagement | Targets, ручной URL fallback, фильтры, inbox, AI предложения | Ответ чужому аккаунту невозможен без отдельного утверждения; повтор исключён |
| 6. Measurement | Снимки метрик, расходы, бюджетный stop | Доступные данные помечены источником; суммы сравниваются с X Console |
| 7. Friend beta | Второй самостоятельный пользователь | Полная изоляция, независимые OAuth/медиа/jobs, проверка затрат на пользователя |

После каждого этапа: lint, typecheck, профильные тесты, короткая ручная проверка и обновление `IMPLEMENTATION_LOG.md` с решением, расходом и следующим шагом. При провале gate не переходить дальше автоматически.

## 9. Метрики успеха и stop conditions

За 2–4 недели: число успешных запланированных публикаций и сбоев; время, сэкономленное автором; расходы X/AI/хостинг на пользователя; сколько рекомендаций действительно опубликовано; изменение охвата и подписчиков с указанием периода. Продукт полезен, если пользователь продолжает им пользоваться и может объяснить расходы результатами. Остановить дорогой discovery, если API стоимость превышает установленный лимит или большинство кандидатов отклоняются. Не увеличивать расход только ради более красивого dashboard.

## 10. Отложено

Платежи, тарифы, команды/права, агентства, несколько X-аккаунтов в одном workspace, автоответы, массовый поиск по всей сети, auto-follow/likes, сложная атрибуция, отдельный NestJS, Redis/BullMQ. Коммерческий запуск потребует повторной проверки правил X и перехода на разрешённый для коммерческого использования хостинг: Vercel Hobby допускает личное некоммерческое использование. [Vercel fair use](https://vercel.com/docs/limits/fair-use-guidelines).

## 11. Открытые решения

1. Месячный предел на X API/AI и приемлемая точность публикации.
2. Реальная доступность X OAuth, media upload/video, чтения targets и нужных metrics.
3. Продуктовая граница sensitive media и способ соблюдения правил X для аккаунта и публикаций.
4. App auth, scheduler и тарифы хостинга после проверенного cost spike.
5. Что пользователь должен делать при статусе UNKNOWN до следующей попытки.

Решения фиксировать в `docs/decisions.md` с датой и ссылкой на официальный источник. Не подменять эту проверку предположениями.
